FRONTEND TEST INVENTORY
Reviewed: 2026-10-08
Total: 95 helper/API-client tests in 16 files, plus 3 separate browser harnesses
Harnesses: 1 regression test, 1 live deployment smoke test, 1 rendering benchmark

Run from frontend/:
  npm test
  npm run test:browser
Optional live check (real requests to deployed services):
  npm run test:deployed
Optional measurement harness:
  npm run benchmark:render
Single helper file:
  node --test src/data/routes.test.js

Browser scripts require Firefox and geckodriver on PATH or GECKODRIVER_PATH.
Regression/benchmark scripts also accept FIREFOX_BINARY. Live smoke tests accept
SMOKE_SITE_URL and SMOKE_API_URL; default targets are the deployed Render services.
The benchmark accepts BENCHMARK_OUTPUT. Build with an empty VITE_API_BASE_URL to
keep benchmark API URLs local. Each browser harness runs separately from npm test.

Scope: named Node tests and browser harnesses. Loops contain additional scenarios.
Lint/build are separate checks. No performance thresholds are enforced. Actual
browser Back/Forward events are not covered by the regression scenario.

Audit: retained all named tests. Browser storage, JSON imports, request builders,
and rendered interactions protect different boundaries. Frontend Star Force order
and backend combined planning run different implementations. Roll-count and budget
helpers have distinct units and edge cases. Similar assertions alone do not make
these tests redundant. Live smoke and benchmark were reviewed, not rerun in this audit.
Latest local run: all 95 helper tests and the integrated browser regression passed.

Inventory policy: one entry per current named test, grouped by source file.
Historical counts/change logs removed. Descriptions summarize assertions and do
not claim exhaustive input coverage. Update the relevant entry after test changes.

Tests: 22

  Verifies the four-second hat minimum reaches the API payload.

  Checks requests and restored equipment use the catalog boss flag, preserve recorded flame
  lines, and continue honoring overrides for items with a manual flame type.

3. secondary stat weights migrate saved divisors and send points per stat
  Checks legacy divisors 10 and 4 become multipliers 0.1 and

4. Xenon requests carry three primary stats and no secondary stats
  Builds a Xenon request with STR, DEX, and LUK as primary stats, no secondary stats, and

5. MVP rank is validated in restored settings and serialized in requests
  Preserves Diamond+ MVP, falls back to none for an invalid rank, and includes the restored
  rank in upgrade requests.

6. consecutive Astra steps combine into 0–10 with total costs, gains and efficiency
  Merges ten consecutive steps into a 0-to-10 range, totaling gain 20, cost 5,500, and
  attempts 55; recalculates gain/cost without mutating the input.

7. grouping preserves interruptions, separate slots, gaps and reversed star order
  Keeps rows separate across intervening items, different ring slots, missing stars,
  reversed steps, and unavailable values; accepts empty input.

8. Astra 10–15 prerequisites precede higher-efficiency 15–17 upgrades
  Reorders shuffled Astra steps so 10-to-15 prerequisites precede later stars, then groups
  the continuous 10-to-17 range without changing the input.

9. equal-efficiency choices preserve ranking priority and separate equipped slots
  Breaks efficiency ties using original ranking priority while treating ring-1 and ring-2
  independently; accepts an empty queue.

10. six-star lookahead chooses a later payoff over another item and commits its prerequisites
  Chooses a six-step range whose final gain beats another item, includes every
  prerequisite, and leaves the seventh step until after that competitor; preserves input.

11. lookahead stops at six stars and does not use a seventh-star payoff
  Does not choose a low-star range solely for a payoff seven steps away. The better
  immediate competitor stays first.

12. range efficiency includes expensive prerequisites instead of averaging per-star ratios
  Ranks total gain divided by total cost; a cheap final upgrade cannot hide an expensive
  prerequisite.

13. Astra below 15 can win on post-15 gains beyond the normal six-star horizon
  Allows a below-15 item to win through post-15 gains outside the usual six-step horizon,
  including all 17 steps and their combined cost/gain.

14. post-15 gains do not win when the full prerequisite cost is too high
  Keeps another item first when reaching the post-15 payoff is too expensive after counting
  prerequisites.

15. lookahead can choose fewer than six stars and reassesses after the chosen range
  Can commit a two-star range, then reconsider other items instead of forcing a six-star
  block.

16. replacement costs reach requests and grouped boom totals affect ordering
  Requests carry Astra defaults and zero overrides. Grouped ranges sum fractional booms and
  replacement spending; efficiency and ordering use total cost.

17. upgrade requests preserve duplicate slots and convert recorded rolls to API fields
  Builds separate ring entries with their stars and limits, preserves modes/safeguards and
  explicit false boss status, converts numeric strings, and omits empty potential rows.

18. upgrade requests map overall and weapon types, retain clean offense and default empty rolls
  Maps overall potential to outfit and weapon potential to weapon, preserves base weapon
  offense, and defaults missing stars/rolls to zero/empty arrays.

19. saved upgrade settings accept zero weights and recover from invalid values
  Preserves zero as a valid weight while replacing invalid cube type, negative weight, and
  infinite weight with defaults.

20. upgrade selections survive restoration and reach the API
  Restores valid upgrade categories and passes them to the API, removes obsolete flame
  type/cost settings, and defaults when every saved category is invalid.

21. fixed ring four is excluded from all upgrade requests
  Ensures requests omit ring-4 while retaining another ring slot, so the fixed skill ring
  cannot receive enhancement recommendations.

22. cube sale persists and reaches upgrade calculations
  Checks both true and false sale settings survive restoration and reach the upgrade API
  request. A saved string 'true' is rejected as a sale flag and falls back to false.
